## Learned

- `AgentTool(RemoteA2aAgent(...))` makes a remote agent look like any tool to the model; behind it is an HTTP call. `sub_agents=[...]` would **transfer** the conversation instead.
- Each agent has its **own session state**; a remote peer can't write into the caller's state, only its reply comes back.
- Locally the caller needs the **address**; in the cloud it would need only the **name** (Agent Registry), and identity, IAM and the gateway would decide whether the call is allowed (Part C, **docs/guess**).

## Q&A: finding an agent "by name"

- **What if several agents have similar names?** "By name" means the **resource name** (`projects/.../locations/.../agents/ID`), which is unique like a primary key. Display names can collide; resource names can't.
- **Lookup vs search:** pin the resource name in config for agents that act (`AgentRegistry(...).get_remote_a2a_agent(RESOURCE_NAME)`, **verified** signature in ADK 2.15); let the model search only for advice (skills).
- **How does it know it's allowed?** It doesn't need to: finding is not permission. The gateway rule (`destination.agent_registry.agent.name == RESOURCE_NAME`) and IAM on the target decide at call time; default deny blocks look-alikes. The agent should handle a 403 openly.
- `get_remote_a2a_agent` resolves **how** to authenticate from the agent's IAM bindings in the registry (**verified** in the code's docstring); it grants nothing.
